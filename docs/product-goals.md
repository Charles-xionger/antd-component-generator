# Prompt Web 产品目标与成熟度标准

## 1. 产品愿景

让不熟悉工程实现的人，也能把一个明确的业务想法变成可修改、可发布、可交给他人使用的 Web 应用。

Prompt Web 的价值不以生成代码量、模型数量或 Agent 数量衡量，而以最终结果衡量：

> 用户是否得到了目标页面，是否能完成关键操作，是否能发布为稳定 URL，以及其他人是否可以直接使用。

## 2. 当前产品边界

### 优先服务的用户

- 希望快速验证业务工具的产品经理或业务负责人。
- 需要搭建项目台账、运营看板、客户跟进等轻应用的企业员工。
- 希望理解 AI Agent 产品设计与交付过程的开发者。

### 优先解决的任务

- 数据看板与统计页面。
- 表格、筛选、表单和详情组成的业务台账。
- 具有真实数据持久化的轻量 CRUD 应用。
- 可以通过固定 URL 分享和持续迭代的内部工具。

### 暂不追求

- 覆盖所有前端框架、编程语言和应用类型。
- 与通用 AI 编程产品比拼模型规模或插件数量。
- 复杂 ERP、强事务系统或高并发互联网业务。
- 在核心旅程稳定前增加更多 Agent 角色和炫技功能。

## 3. 北极星用户旅程

```text
选择案例或描述业务目标
  → 系统整理页面 / 数据 / 操作 Brief
  → 用户确认或修改关键约束
  → 工作区持续显示页面和生成进度
  → 用户选中目标区域进行局部修改
  → 系统自动检查关键流程
  → 用户发布通过检查的版本
  → 获得稳定 URL 并分享给他人使用
```

这条旅程是产品信息架构、交互设计和 Agent 调度的共同主线。不能要求用户理解 Sandbox、Artifact、Migration 或 BuildJob 才能完成任务。

## 4. 成熟产品体验原则

### 页面是主角，聊天是控制器

- 生成页面后，预览占据主要视觉区域。
- 聊天用于表达目标、解释变化和控制 Agent，不用于堆叠内部日志。
- 代码、详细工具调用和诊断信息放在二级视图。

### 一个工作区完成完整任务

- 计划、预览、修改、版本和发布共享同一项目上下文。
- 浏览器快速预览与真实全栈预览在用户侧统一为“预览”，只在状态中解释可用程度。
- 分享预览和正式发布有明确区别，但不使用基础设施术语解释。

### Agent 行为必须可理解

前台统一使用以下阶段：

1. 理解需求
2. 设计应用
3. 构建页面与数据
4. 检查可用性
5. 准备发布

每个阶段回答三个问题：系统正在做什么、已经完成什么、用户是否需要行动。

### 修改必须可控

- 支持在预览中选择目标区域再提出修改。
- 执行前说明影响范围，完成后突出本次变化。
- 每次修改形成 Checkpoint，可以查看 Diff 和一键撤销。
- 新修改不能静默覆盖当前已发布版本。

### 发布必须形成成功时刻

- 发布前展示目标版本和检查结果。
- 发布中持续展示真实状态，不使用无限 Loading。
- 发布后展示 URL、复制、打开、二维码和继续修改入口。
- 失败时保留旧版本在线，并给出可以执行的恢复动作。

## 5. 现场演示“不翻车”标准

### 功能稳定性

- 黄金案例连续运行 10 次，均能完成生成、真实预览和发布。
- 每次生成的核心页面、数据实体和主操作保持一致。
- 构建或模型失败时可以重试或回到最近成功 Checkpoint。
- 生产访问地址在重新发布和回滚后保持稳定。

### UI/UX

- 1440px 桌面演示无布局跳动、遮挡和不可见主操作。
- 390px 手机预览无横向滚动，关键按钮可见且可操作。
- Loading、Empty、Error、Success 四类状态均有完整设计。
- 主按钮在每一步只有一个，下一步不依赖讲解者寻找。
- Console error、失败网络请求和不可访问资源为零。

### 演示准备

- 提供预置账号、固定黄金案例和可重置演示数据。
- 演示前自动执行环境检查：模型、数据库、Worker、Sandbox、域名和证书。
- 保留一个已经构建成功的回退版本；现场生成失败时仍可继续演示修改和发布。
- 准备一条主脚本和一条备用脚本，避免临场自由发挥扩大范围。

## 6. 产品指标

### 核心结果指标

- 首次生成命中率：首版满足核心页面与主流程的比例。
- Time to First Usable Preview：从提交目标到第一个可操作预览的时间。
- 修正轮数：从首版到用户确认目标页面所需的对话轮数。
- 生成到发布转化率。
- 发布成功率与发布后可访问率。

### 体验诊断指标

- 用户在哪个阶段退出或重新输入需求。
- 局部修改成功率和撤销率。
- 构建失败、运行时失败和验收失败的分布。
- 自动修复成功率。
- 发布后页面错误率和关键操作成功率。

## 7. 迭代路线

### P0：建立稳定演示闭环

- 重写首页定位、案例入口、空状态与首次引导。
- 建立统一主工作区，以预览为核心。
- 固定黄金案例的 Prompt、数据、视觉基线和验收脚本。
- 将内部 Agent 事件映射为用户可理解的阶段和结果。
- 完成发布成功页、失败恢复和无登录访问验证。
- 建立 Playwright 主旅程和 UI 截图基线。

### P1：提高页面命中率和修改效率

- 可视化 Brief：页面、数据、主操作和视觉方向。
- 三套高完成度设计预设。
- 预览内选区修改和变化高亮。
- Checkpoint 时间线、版本 Diff 和撤销。
- 响应式、Loading、Empty、Error 等关键状态自动验收。

### P2：形成完整产品

- 项目首页与案例 Gallery。
- 统一发布中心和最小使用数据。
- 团队组件库、内部 API 和部署配置。
- 基于用户反馈的生成质量评估集。
- 完整的日志、指标、告警和自动回滚策略。

## 8. Agent 能力与产品价值的关系

Agent 能力只有在改善用户结果时才进入主线：

| Agent 能力 | 产品问题 | 可展示证据 |
|---|---|---|
| 意图路由 | 区分新建、修改、问答和修复 | 同一输入框进入正确任务流 |
| Structured Output | 降低需求和生成结果漂移 | 可视化 Brief、RequirementSpec、AppBlueprint |
| Tool Use | 让模型真正执行构建与发布 | 命令、构建、预览、发布的真实事件 |
| Checkpoint | 修改失败后安全恢复 | 时间线、Diff、一键撤销 |
| Evaluation | 判断页面是否真的完成 | API 场景、浏览器 E2E、截图和检查结果 |
| Human-in-the-loop | 保留关键业务决定权 | Brief 确认、发布确认和 Stage 验收 |

面试表达应先展示用户结果，再解释这些机制为什么存在，最后用失败案例和指标证明迭代效果。
