# Prompt-to-App 产品开发计划

> 计划基线：2026-09-26  
> 产品目标：让不会写代码的企业业务人员，通过描述和确认业务需求，得到一个可直接使用、可持续修改和可发布的内部轻应用。

本计划不按技术模块、开发时长或实现难度排序。版本只以用户能否完成一个新的业务闭环来划分；数据库、协议、Agent、Sandbox 和发布能力都是实现业务结果的手段，不单独作为版本价值。

## 1. 产品交付原则

1. **先识别意图，再决定是否开发。** 咨询、修改、修复、发布和创建应用走不同路径，不能由一个 Architect Prompt 混合判断。
2. **先澄清并确认需求，再生成。** AI 面向业务人员询问缺失信息，输出可读的需求摘要；用户确认后才消耗资源开发。
3. **一次交付完整闭环。** 新应用至少同时包含页面、数据模型、服务端操作、业务规则、真实数据和可运行预览，不交付只有页面或只有数据 API 的半成品。
4. **以业务场景验收。** 验收一个真实流程能否完成，而不是某张表、某个接口或某个 Agent 是否存在。
5. **生成的是轻应用，不是组件。** Artifact 必须表达完整应用版本，而不仅是一组 React 文件。
6. **修改不能破坏已有结果。** 代码、Schema 和发布可以演进，已有业务数据必须持续保留。
7. **求职项目聚焦核心能力。** 登录方式、复杂权限、组织同步、计费和商业化不进入当前主线；现有 GitHub 登录继续使用。

## 2. 当前基线

### 已经可用

- 自然语言和图片输入。
- Architect → Coder 的前端生成链路。
- 多文件 React 应用、Sandbox 实时预览和版本保存。
- Project、Primary Thread、ArtifactVersion 与 Deployment。
- 独立子域名发布、重新发布、回滚和下线。
- Go 1.24 固定 Scaffold、BuildJob 控制面和传统 PostgreSQL 关系模型方案。
- 原 Data Manifest 的校验与 Schema Diff 思路保留，但 JSONB DataRecord 路线停止实施。

### 当前核心缺口

- 系统收到任何消息后仍主要按“是否生成前端代码”判断，没有稳定的产品意图路由。
- AI 不会在生成前完成业务需求澄清和人工确认。
- Architect 只设计前端文件，没有统一描述页面、数据、API、业务规则和验收场景的应用蓝图。
- Coder 仍以 Mock Helper 和前端文件为中心，不能生成完整服务端业务行为。
- 真实数据底座尚未接入生成、预览和发布主链路。
- 验证标准偏向代码能否构建，不能证明业务流程真的可用。

## 3. 版本路线

| 版本 | 用户获得的结果 | 状态 |
| --- | --- | --- |
| Foundation | 项目可生成、预览、保存版本并发布静态应用；真实数据底座已建立 | 已完成 |
| App V1 | 从模糊业务描述，经澄清确认后，生成一个带真实数据和服务端业务规则的可运行轻应用 | 主链路已实现 |
| App V1 Publish | 将同一个轻应用发布到独立地址，线上真实数据可持续使用，重新发布不丢数据 | 已实现，待生产环境验收 |
| App V1 Evolve | 通过对话修改页面、数据结构和业务规则，系统验证影响并安全升级 | 待开始 |
| Portfolio Release | 用多个代表性场景证明通用生成能力，完成稳定演示、失败恢复和架构说明 | 待开始 |

原 DG-0.1 与 DG-0.2 作为 Foundation 的已完成工程基础保留，不再继续以 DG-0.3、DG-0.4 的技术层级拆分产品版本。未完成的数据能力直接并入对应业务闭环。

## 4. 当前迭代：App V1

### 4.1 必须解决的问题

业务人员通常只能描述目标，不能一次给出完整的数据结构、页面、接口和边界条件。系统需要先理解用户是否真的要创建应用，再帮助用户把模糊想法变成可确认的业务需求，并最终交付一个能完成核心流程的应用。

### 4.2 目标用户结果

用户输入：

> 帮我做一个 AIGC 短剧分镜团队的工时和产能统计应用，我想按人员、项目和时间查看不同维度的图表。

系统应完成：

1. 识别为“创建应用”，而不是普通咨询或修改现有项目。
2. 询问会改变统计结果的关键问题，例如工时如何记录、分镜产量如何计算、返工是否计入产能、统计周期和负责人希望查看哪些指标。
3. 汇总业务目标、使用者、核心流程、数据对象、业务规则和验收场景。
4. 等待用户明确确认；未确认前不进入代码生成。
5. 根据确认结果生成完整应用蓝图。
6. 生成人员、短剧项目、分镜任务和工时记录的数据模型，以及录入、修改、统计和聚合所需的服务端操作。
7. 在预览中录入真实工时和分镜产量，刷新后数据仍然存在。
8. 自动计算总工时、完成分镜数、有效分镜数、返工数和人均/人时产能，并按人员、项目、日期和周期生成图表。
9. 保存本次需求、蓝图、代码和数据结构之间的版本关系。

### 4.2.1 验收场景的数据口径

首个验收案例默认采用以下业务口径，AI 在需求澄清时允许用户调整：

- **人员**：分镜制作人员，包含姓名、所属小组和在职状态。
- **短剧项目**：包含项目名称、集数或批次、负责人和项目状态。
- **分镜任务**：关联项目与制作人员，记录计划分镜数、完成分镜数、通过分镜数、返工分镜数和完成日期。
- **工时记录**：关联人员、项目和日期，记录投入小时数及备注。
- **有效产能**：通过验收的分镜数量。
- **人时产能**：有效产能 ÷ 对应投入工时；工时为零时不得生成无效比值。

应用至少包含：

- 工时与产量录入页面。
- 人员和项目基础数据页面。
- 产能统计看板。
- 可按日期范围、人员、小组和项目筛选的数据视图。
- 按人员排名、项目对比、每日/每周趋势和工时—产能关系展示的图表。

服务端必须保证工时与数量不能为负数、引用对象真实存在、重复提交不产生重复记录，并使用统一统计口径返回聚合结果。前端不得自行拼接出另一套指标口径。

### 4.3 LangGraph 主链路

```text
User Input
  → Intent Router
  → Business Analyst
  → Requirement Check
      → 信息不足：向用户提问 → Business Analyst
      → 信息完整：生成 Requirement Spec
  → Human Confirmation
      → 用户调整：Business Analyst
      → 用户确认：Solution Architect
  → App Blueprint
  → Full-stack Coder
      → Data Schema
      → Backend Operations / Business Rules
      → Frontend
  → Integration Validator
      → 失败：Diagnosis / Repair → 重新验证
      → 通过：真实数据预览
```

节点是独立职责，不强制对应不同模型。第一版可以由同一模型在不同节点使用不同 Prompt 和结构化输出，但状态、输入输出和路由必须分离。

### 4.4 意图路由

首版识别以下意图：

- `CREATE_APP`：创建新轻应用。
- `MODIFY_APP`：修改现有应用的页面、数据或业务规则。
- `FIX_APP`：修复构建、运行或业务行为问题。
- `EXPLAIN_APP`：解释应用、代码或实现。
- `APP_OPERATION`：发布、回滚或下线。
- `GENERAL_CHAT`：普通交流，不进入开发。
- `UNSUPPORTED`：当前无法交付的请求，说明边界。

路由结果必须包含置信度、是否需要澄清、引用的 Project，以及从输入中识别出的业务能力。低置信度时询问用户，不猜测并启动开发。

### 4.5 Requirement Spec

业务分析节点输出用户可读且机器可执行的需求规格：

- 应用名称和业务目标。
- 目标使用者。
- 核心业务流程。
- 数据对象及关键字段。
- 业务状态和规则。
- 异常与边界情况。
- 明确不包含的内容。
- 可验证的验收场景。

澄清问题只询问会改变应用结果的信息。视觉细节、技术选型和非核心配置使用平台默认值，不把技术决策转嫁给业务用户。

### 4.6 App Blueprint

Solution Architect 不再输出单纯的前端文件计划，而是统一应用契约：

```text
App Blueprint
├── Product：目标、用户、流程、验收条件
├── Pages：页面、导航、操作和状态
├── Entities：实体、字段和稳定标识
├── Backend Operations：查询、命令和输入输出
├── Business Rules：必须由服务端保证的业务约束
├── Data Evolution：相对当前版本的数据结构变化
└── Test Scenarios：正常、异常和边界场景
```

Frontend、Backend、Data 和 Validator 必须读取同一份 Blueprint，禁止各自重新猜测需求。

### 4.7 完整轻应用生成

App V1 使用平台版本化的 Go Scaffold。AI 生成应用专属的 Go 业务层、关系模型、SQL Migration 与测试；Go 二进制内嵌 React 产物并同时提供页面和同源 API。

第一版生成物至少包含：

- React 页面和交互。
- App Blueprint 与版本化关系型 SQL Migration。
- 查询与写入操作定义。
- 服务端校验和业务规则。
- `@prompt-web/app-runtime` 语言无关调用契约。
- Loading、Empty、Error 和 Success 状态。
- 核心业务场景测试。

平台负责构建约束、Schema 隔离、Migration 校验和发布生命周期；生成的 Go service/repository 负责应用数据访问、事务、幂等和业务规则。每个应用使用独立 DRAFT/PROD Schema，不再通过共享 Data Gateway 或 JSONB Record 运行。

### 4.8 真实预览

本迭代同时完成以下能力，不再拆成若干“底座版本”：

- Generator 与 Sandbox 使用新的应用协议。
- Sandbox 使用内存 Runtime 即时预览；后台 Go 全栈预览连接 DRAFT 关系表。
- DRAFT 查询、写入、聚合和应用业务所需的数据操作。
- 支持验收场景需要的多实体引用、分组聚合、日期范围筛选和排序。
- 稳定 operation ID、请求幂等与数据库约束。
- 版本化 SQL 自动创建或安全升级 DRAFT Schema。
- 生成的服务端业务规则在预览环境执行。
- 页面刷新后数据仍存在。

### 4.9 验收门槛

以下条件全部满足才算 App V1 完成：

- 咨询或闲聊不会触发代码生成。
- 模糊需求会先产生必要的业务问题。
- 用户未确认需求时不会进入开发。
- 确认后可以一次生成可运行的完整应用。
- 预览中能够完成一个端到端业务流程。
- 刷新页面后数据仍存在。
- 同一批工时和分镜数据在表格、指标卡与不同维度图表中的统计结果一致。
- 切换人员、项目和日期维度时，聚合结果与原始记录可核对。
- 核心业务规则由服务端保证，绕过前端也不能破坏规则。
- 生成失败能够定位到需求、蓝图、数据、后端或前端层，并进入修复循环。
- 代码版本、Blueprint 和 Schema Version 可以追溯。

### 4.10 本迭代明确不投入

- 将 GitHub 登录迁移为飞书登录。
- 组织、部门和成员同步。
- 复杂 RBAC、字段级权限和审批引擎。
- 应用市场、计费和商业化运营。
- 任意语言、任意依赖和无限制后端代码执行。
- 为展示架构而建设当前业务闭环不使用的基础设施。

## 5. App V1 Publish：发布后可用

### 用户结果

用户把已验证的轻应用发布到独立地址，生产环境完成相同业务流程；后续重新发布页面或逻辑时，已有生产数据保持不变。

### 必须同时交付

- Deployment 绑定 Artifact、Blueprint 和生产 Schema Version。
- 发布前执行构建、业务场景验证和 Schema Diff。
- 安全的数据结构变化自动应用；危险变化阻止发布并说明业务影响。
- 生产 Runtime 执行生成的服务端操作和业务规则。
- 第一次发布建立空生产数据结构，不默认复制草稿测试数据。
- 重新发布、回滚和下线不删除业务数据。
- 迁移或构建失败时旧版本继续在线。

### 验收场景

- 发布 AIGC 短剧分镜产能应用后，可以录入生产工时和分镜产量并查看统计看板。
- 第二次发布修改看板布局和图表样式，已有人员、项目、工时和产量数据不变。
- 新增可选字段后重新发布，旧记录仍能读取。
- 删除关键字段或修改不兼容类型时，发布被阻止并解释影响。
- 回滚页面和逻辑版本不会反向删除生产字段和记录。

## 6. App V1 Evolve：持续修改

### 用户结果

用户不需要重建项目，可以继续用业务语言修改页面、数据和规则，并安全得到新版本。

### 必须同时交付

- `MODIFY_APP` 与 `FIX_APP` 使用当前 Requirement Spec、Blueprint、代码和 Schema 作为上下文。
- Change Analyst 识别本次变更影响的页面、实体、接口、规则和测试。
- 只有受影响部分重新生成，未修改能力保持稳定。
- 数据结构变化生成清晰的升级结果，不静默删除或覆盖数据。
- Validator 回归旧场景并验证新增场景。
- 用户可以比较版本并选择发布或回滚。

### 验收场景

在既有分镜产能应用中增加“分镜难度系数”和“按难度折算产能”：旧工时与产量数据保留，新旧统计口径有明确版本说明，未涉及的录入、人员和项目管理功能不回归。

## 7. Portfolio Release：证明产品成立

最终版本不以功能数量验收。AIGC 短剧分镜产能统计作为主案例，完整证明需求澄清、数据录入、服务端统计、多维分析、发布和持续修改能力；再用两个差异化案例验证生成链路不是针对主案例硬编码：

1. **AIGC 短剧分镜产能统计**：主案例，证明多实体业务数据、统一指标口径、分组聚合和多维图表。
2. **客户跟进管理**：验证状态流转、跟进记录和统计视图。
3. **库存出入库**：验证数量校验、业务操作和数据一致性。

每个案例都必须走完：

```text
模糊描述 → 澄清 → 确认 → 全栈生成 → 真实预览
→ 发布 → 使用生产数据 → 修改 → 重新发布 → 数据保持
```

求职演示重点是产品如何把非技术人员的业务目标转化为可验证应用，以及系统如何约束生成、执行规则、保护数据并完成发布，而不是 Agent 数量或基础设施复杂度。

## 8. 结果驱动的开发顺序

开发任务从验收场景反向拆解：

1. 先固定 App V1 的 AIGC 短剧分镜产能统计验收数据、指标公式和端到端脚本。
2. 定义 Intent Result、Requirement Spec 和 App Blueprint 契约。
3. 重构 LangGraph，使“等待用户回答”和“等待用户确认”成为正式状态。
4. 让 Full-stack Coder 基于 Blueprint 生成数据、后端和前端。
5. 打通 DRAFT 写入、服务端规则执行和 Sandbox 真实预览。
6. 建立自动验证与修复循环，跑通完整验收脚本。
7. 只有当一个真实业务流程端到端通过后，才扩展更多字段类型、查询能力或场景。

任何任务如果不能直接支撑当前验收场景，应从当前迭代移出，而不是因为“以后可能需要”提前开发。

## 9. 质量与回退原则

- 结构化契约必须进行 Schema 校验，失败不能静默进入下一节点。
- 每个生成请求可追踪到用户确认的 Requirement Spec。
- 业务规则至少包含正常、冲突和非法输入测试。
- 新协议上线时保留现有 V1 项目的读取与发布能力。
- 数据库继续采用 expand-and-contract；应用回滚不回滚或覆盖业务数据。
- 新版本构建、迁移或验证失败时，保留当前可用版本。
- 日志记录业务阶段、节点结果和失败原因，不记录密钥或敏感数据。

## 10. 当前下一步

App V1 以三个核心契约驱动生成与发布：

1. `IntentResult`：系统为什么进入或不进入开发。
2. `RequirementSpec`：用户确认了什么业务结果。
3. `AppBlueprint`：前端、后端、数据和测试共同实现什么。

意图识别、澄清确认、统一 Blueprint、React/Go/SQL 生成、Sandbox 交互预览、DRAFT 容器验收和 PROD 发布代码路径已经实现。AIGC 分镜产能案例已通过本地 PostgreSQL + Go 容器的 10 步 API 验收和容器重启持久化验证。

下一步是在真实 Traefik 域名与生产数据库账号体系中执行发布演练，验证 Socket Proxy 权限、精确 Host 路由、旧版本保活和失败切流；通过后进入 App V1 Evolve，重点实现跨 ArtifactVersion 的 Migration 差异校验与数据升级预检。具体运行时边界见 [Go 全栈轻应用运行时](../go-fullstack-runtime.md)。
