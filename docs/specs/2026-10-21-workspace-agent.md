# P0 Workspace Agent：从一次性代码生成到可恢复的工作区执行

> 状态：待用户 review。范围仅为 P0；Preview 诊断自动回流与专门的 Bug Fix 子 Agent 属于 P1。

## 问题陈述

用户创建或修改应用时，系统要求模型一次输出带 `<boltArtifact>` 标签的完整项目，再从消息文本中提取文件。任何标签、JSON 或单个文件的截断都可能使整次生成失败。修复时系统把上一版完整产物重新放进上下文，要求模型再次输出完整快照；即使错误只在一个文件中，也无法可靠地定位和定向修改。代码、修复过程和 UI 消息混用同一段文本，刷新或连接中断后也缺少可继续执行的工作区状态。

现有的 `ArtifactVersion` 保存和 Go Preview BuildJob 提供了后半段能力，但版本可能在真实构建前创建，Preview 的编译或运行错误不会自动回到编码循环。用户因而难以判断“代码已提交”“预览通过”和“任务完成”各自意味着什么。

## 解决方案

每次开发任务从项目当前版本创建一个隔离的 Draft Workspace。数据库保存工作区的当前文件、修订号、计划、诊断、工具事件和检查点；隔离执行环境从指定修订号还原文件，运行受控校验命令。模型通过工具按需列出、搜索、读取和修改文件，文件工具的成功结果才改变工作区。对话保留目标与过程摘要，不承载完整代码。

**稳定生成协议**：新任务不再让模型生成 `<boltArtifact>`、完整项目 JSON 或自定义事件文本供正则提取。模型只能通过具名、Schema 约束的 `write_file` / `patch_file` 等工具提交单文件变更；结构化业务文件可使用对象参数与确定性序列化，避免让模型手写易错的 JSON 外壳。工具执行器在收到完整调用、校验参数与工作区修订后，才原子写入数据库并返回结果。流式参数片段、普通 assistant 文本、未闭合调用及模型自行描述的 `file.changed` 均不产生文件变更。运行时在工具真正成功后生成 `file.changed` 等 Item/Event，供 UI 展示和断线恢复。事件流是执行记录与展示协议，不是另一种代码传输外壳。

首次生成、普通修改及用户直接提出的现有代码 Bug Fix 均由同一个主 Agent 循环处理。该循环读取真实状态、决定下一步、调用工具、检查结果并继续，直到通过 P0 提交门槛或以明确原因停止。通过契约、Schema、Migration 静态检查及适用的 TypeScript/Go 编译后，系统从确定的工作区修订号创建不可变 `ArtifactVersion`。Go 全栈版本随后启动现有 Preview BuildJob；静态版本继续由浏览器 Sandbox 预览。P0 展示 Preview 结果；Preview 失败时保留 Draft Workspace 与诊断，不自动重新进入 Agent。P1 再加入 Preview 诊断回流和专门的 Bug Fix 子 Agent。

## 用户故事

### 创建与修改

原 US-7（人工编辑）与 US-12（运行中补充要求）已移到文末“下一次需求记录”，编号保留空位，避免与既有 review 记录混淆。

- **US-1** 作为首次创建应用的用户，我想看到 Agent 在工作区逐步建立文件，以便单个文件出错时不丢失其他已完成工作。
- **US-2** 作为修改现有应用的用户，我想让 Agent 以当前可用版本为起点，以便只改变与需求有关的文件。
- **US-3** 作为要求修复现有代码问题的用户，我想让主 Agent 检查并定向修改相关文件，以便 P0 就能处理明确的代码错误。
- **US-4** 作为使用静态应用的用户，我想让新流程继续生成、修改和验证 React 页面，以便升级后不失去现有能力。
- **US-5** 作为使用 Go 全栈应用的用户，我想让新流程继续维护前端、后端、Migration 与验收文件，以便升级后不失去现有业务能力。
- **US-6** 作为编辑项目的用户，我想在代码面板读取 Draft Workspace 的最新文件和修订，以便看到 Agent 实际写入的内容。

### 执行与恢复

- **US-8** 作为等待复杂任务的用户，我想看到计划、当前步骤、文件变化和检查结果，以便理解任务进展。
- **US-9** 作为刷新页面或短暂断线的用户，我想恢复任务状态与事件进度，以便继续观察同一任务。
- **US-10** 作为任务中断的用户，我想从持久化检查点继续，以便不重新生成已经写好的文件。
- **US-11** 作为需要停止任务的用户，我想取消尚未完成的执行，以便停止后续模型调用与工具写入，并保留已完成的 Draft。
- **US-13** 作为在多个项目工作的用户，我想让不同项目并行处理，同时同一项目只有一个活跃写入任务，以便修改互不冲突。
- **US-14** 作为重复提交或网络重试的用户，我想让相同请求与工具调用只生效一次，以便不会重复写文件或创建版本。

### 诊断、提交与预览

- **US-15** 作为遇到生成错误的用户，我想看到具体文件、位置和错误原因，以便知道系统正在修什么。
- **US-16** 作为遇到局部错误的用户，我想让 Agent 只读取和修改相关文件，以便避免全量重写导致的新错误。
- **US-17** 作为遇到重复错误的用户，我想让任务停止盲目重试并报告无进展，以便不持续消耗时间与额度。
- **US-18** 作为准备查看版本的用户，我想只有通过 P0 提交检查的工作区才能成为正式版本，以便版本列表不会混入不完整产物。
- **US-19** 作为查看新版本的用户，我想区分“代码检查通过并已提交”“Preview 正在验证”和“Preview 失败或成功”，以便准确判断当前可用性。
- **US-20** 作为 Preview 失败的用户，我想保留工作区和错误记录，以便后续手动继续或在 P1 交由自动修复。
- **US-21** 作为查看历史对话的用户，我想继续读取旧 XML 消息，但新任务不再向聊天区发送完整代码，以便历史兼容且新过程清晰。
- **US-22** 作为遇到模型输出中断或格式异常的用户，我想让未完成的写入保持无效、已成功写入的文件不受影响，以便只重试失败的工具调用而不重新生成整个项目。

## 验收标准

- **AC-1** 新建任务在数据库创建独立 Draft Workspace，记录项目、任务、起始版本、当前修订和状态；首次生成可以从空文件集开始。〔覆盖 US-1, US-2〕
  - **怎么验**：后台测试用真实 PostgreSQL 分别创建空项目和已有版本项目，检查工作区文件及起始版本关联；真实页面 BOT-1、BOT-2 检查两条入口。
- **AC-2** 工作区数据库文件是持久化事实来源；从任一已提交修订还原到新的隔离执行目录，文件路径、内容和清单一致。临时目录丢失后仍可重建。〔覆盖 US-1, US-9, US-10〕
  - **怎么验**：后台测试写入多文件后删除执行目录，重新还原并核对文件清单、内容摘要和修订号；真实页面 BOT-3 验证刷新恢复。
- **AC-3** `list_files`、`search_files`、`read_file`、`read_file_range`、`write_file`、`patch_file`、`delete_file` 只访问当前用户有权操作的工作区，拒绝绝对路径、`..`、符号链接越界、非法编码和过大输入；失败不改变修订。〔覆盖 US-2, US-6, US-13〕
  - **怎么验**：后台测试在工具边界验证所有权、路径与大小限制，并核对拒绝前后的修订及文件集合。
- **AC-4** 每次成功的文件变更以原子事务写入文件内容、新修订和对应工具事件；同一 `toolCallId` 重试只返回原结果。基于过期修订的写入返回冲突，不覆盖较新的文件。〔覆盖 US-13, US-14〕
  - **怎么验**：后台测试用真实 PostgreSQL 并发提交、重复调用和故障注入，检查最终文件、递增修订与事件一一对应。
- **AC-5** 首次生成和普通修改的模型输出仅用于选择具名工具及其结构化参数；新任务的文件内容只能由成功的文件工具写入工作区，不通过 `<boltArtifact>`、`<boltAction>`、普通 assistant 消息或模型生成的事件文本解析入库。工具参数采用可校验 Schema；结构化业务文件允许对象参数经确定性序列化写入。〔覆盖 US-1, US-2, US-16, US-21, US-22〕
  - **怎么验**：后台测试用固定脚本模型驱动两类任务，检查工作区变更来源及消息事件；给出伪造 `file.changed` 的模型文本，确认不会写库；真实页面 BOT-1、BOT-2 确认聊天区无完整源文件。
- **AC-6** 首次生成能按文件依赖逐段写入并逐段校验：Go 任务覆盖 Migration、Backend、Acceptance、Frontend；静态任务只执行适用部分。某段失败时已通过部分保持原修订，不要求全项目重写。〔覆盖 US-1, US-4, US-5, US-16〕
  - **怎么验**：后台测试用固定脚本模型在 Acceptance 阶段制造 Schema 错误，确认仅该文件被修复且此前文件内容摘要不变；真实页面 BOT-1 查看阶段与文件记录。
- **AC-7** 普通修改和 P0 直接 Bug Fix 从起始版本读取所需文件、只更新目标文件；未修改文件与起始版本内容一致，最终快照保留完整应用。〔覆盖 US-2, US-3, US-4, US-5, US-16〕
  - **怎么验**：后台测试分别驱动静态和 Go 修改，检查工具读写范围、最终文件差异和完整清单；真实页面 BOT-2 验证目标变化与相邻功能仍在。
- **AC-8** 校验工具提供 JSON 解析、Schema、Migration 静态检查、契约检查、TypeScript/Go 编译及诊断查询；错误至少包含 `source`、`severity`、`code`、`file`、`message`，有位置时包含行列和字段路径，并保留安全截断后的原始编译器信息。〔覆盖 US-15, US-16〕
  - **怎么验**：纯函数测试覆盖 JSON、Zod、TypeScript 和 Go 错误转换；后台测试在真实命令环境产生各类错误，检查诊断关联到工作区修订。
- **AC-9** `acceptance/scenarios.json` 顶层数组错误明确指出 `$` 处预期 `{ scenarios: [...] }`、实际为数组；Agent 可只改该文件并让诊断消失。〔覆盖 US-15, US-16〕
  - **怎么验**：后台测试重现已知失败，检查诊断字段、修复前后差异和 Schema 复验结果。
- **AC-10** 受控命令在隔离执行环境中针对确定的工作区修订运行，具有超时、输出上限和退出码；P0 命令不能绕开文件工具持久化修改源文件，编译产物可丢弃。〔覆盖 US-10, US-14, US-15〕
  - **怎么验**：后台测试运行成功、超时、超量输出和尝试改写源文件的命令，检查诊断、审计事件与数据库源文件不变。
- **AC-11** Agent 循环有执行步数与时长上限；相同阻塞诊断连续出现且目标文件未发生有效变化时停止为 `no_progress`，不误报成功。复杂策略切换不在 P0。〔覆盖 US-17〕
  - **怎么验**：后台测试用固定脚本模型重复同一错误，检查有限次终止、停止原因及模型与工具调用数量。
- **AC-12** 任务的计划、阶段、最后完成的工具调用、工作区修订与诊断持久化；进程或 HTTP 连接终止后，后台执行可被恢复，已完成的文件写入不重做。进行中的只读校验可安全重跑。〔覆盖 US-8, US-9, US-10, US-14〕
  - **怎么验**：后台测试在文件写入后、校验中和提交前分别模拟 Worker 中断，重新领取任务并检查无重复写入或版本；真实页面 BOT-3 检查恢复后的状态。
- **AC-13** 用户取消后任务进入终态，不再发起模型调用或工具写入；已有 Draft 文件和事件保留，重新继续必须创建明确的新执行段。〔覆盖 US-10, US-11〕
  - **怎么验**：后台测试在任务运行中取消并检查状态、后续调用与文件；真实页面 BOT-4 操作取消并刷新。
- **AC-14** Agent 遇到必须由用户决定且无法安全推断的问题时，停止当前执行段并标记 `needs_input`，保留 Draft 与已成功事件；P0 在任务结果中说明待回答问题，用户下一条消息启动新执行段。运行中输入队列、结构化问题卡和确认卡留到下一次需求。〔覆盖 US-10, US-11〕
  - **怎么验**：后台测试用固定脚本模型触发待确认分支，检查没有继续写入、Draft 保留、状态与结果摘要；真实页面 BOT-4 验证问题可见并能在下一执行段继续。
- **AC-15** 同一项目同一时刻仅一个 Agent 任务持有写入权；第二个标签页的写入任务进入队列或返回明确冲突，不会产生分叉的“最新文件”。不同项目允许并行。〔覆盖 US-13〕
  - **怎么验**：后台测试用两个连接并发写同一项目及不同项目；真实页面 BOT-5 在两个标签页验证状态提示与排队/冲突结果。
- **AC-16** P0 代码面板只展示工作区文件与修订，不提供人工编辑、保存或暂停 Agent 的入口；Agent 进行中普通输入框不伪装成可立即介入当前工具调用。〔覆盖 US-6, US-8〕
  - **怎么验**：组件测试检查文件内容来源、只读状态与输入框提示；真实页面 BOT-1、BOT-3 检查工作区视图。
- **AC-17** 只有确定的工作区修订通过必要文件、Schema、关联契约、Migration 静态检查、TypeScript/Go 编译且没有阻塞诊断时，才创建一个不可变 `ArtifactVersion`；失败 Draft 不进入版本列表。〔覆盖 US-4, US-5, US-18〕
  - **怎么验**：后台测试分别提交有效静态、有效 Go 和多种失败 Draft，检查数据库版本数、文件快照、修订摘要与阻断原因；真实页面 BOT-1、BOT-2 检查版本结果。
- **AC-18** 相同任务重复提交只产生一个 `ArtifactVersion`，版本文件来自已校验修订，不受提交期间后续写入影响。〔覆盖 US-14, US-18〕
  - **怎么验**：后台测试并发提交和故障恢复，检查幂等键、修订锁定和版本文件摘要。
- **AC-19** Go 全栈版本创建后才排队现有 Preview BuildJob；静态版本从已提交文件进入浏览器 Sandbox 预览。任务 UI 分别显示“代码已提交”“Preview 验证中”“Preview 成功”或“Preview 失败”。Preview 失败保留 Draft 与错误，但 P0 不自动调用 Agent 修复。〔覆盖 US-19, US-20〕
  - **怎么验**：后台测试检查 Go 版本与 BuildJob 创建顺序、静态文件投送、失败状态映射和不触发新模型调用；真实页面 BOT-6 检查两类 Preview 结果。
- **AC-20** 新任务使用持久化的 `sessionId`/`turnId`/`itemId`/`toolCallId` 与单调事件序号；计划、工具、文件变更、命令、诊断、版本结果各有独立 Item，重连从已见序号续传且不重复展示。〔覆盖 US-8, US-9, US-21〕
  - **怎么验**：后台测试复用现有发布 SSE 测试方式检查快照、增量、所有权、顺序和去重；真实页面 BOT-3 验证刷新与断线恢复。
- **AC-21** 聊天区只展示面向用户的目标、进度和结果摘要；代码面板按工作区文件 API 展示内容。历史 XML 消息继续可读，但新任务不依赖 XML 标签判定生命周期。〔覆盖 US-6, US-8, US-21〕
  - **怎么验**：组件测试检查各类 Item 的摘要与代码面板数据来源；真实页面 BOT-1、BOT-3、BOT-7 检查新旧任务呈现。
- **AC-22** 所有工作区 API、事件订阅和版本提交均验证项目所有权；模型生成的路径、命令参数和日志不能读取其他项目或泄露运行环境 Secret。〔覆盖 US-13, US-15〕
  - **怎么验**：后台测试以另一用户访问、越界路径和注入测试 Secret；真实页面 BOT-5 验证无跨项目信息。
- **AC-23** 只有接收完整、Schema 合法、权限及预期修订检查通过的工具调用，才允许执行单文件写入；流式参数片段只可显示为进行中，不得提前落库。调用截断、参数不合法、传输中断或工具失败时，目标文件内容、修订与 `file.changed` 成功事件均不变；此前已成功的其他文件保持原样，可从失败调用继续。成功事件由工具执行器生成并关联 `toolCallId`、文件、前后修订及内容摘要。〔覆盖 US-1, US-14, US-22〕
  - **怎么验**：后台端到端接缝依次注入不闭合的模型工具调用、错误参数、写入前中断及有效的单文件调用；核对数据库修订、文件内容、事件与重试结果，并确认不需要完整项目重新输出。

## 实现决策

- **事实来源**：数据库中的 Draft 文件及递增修订是持久化事实来源；临时文件系统是指定修订的执行投影，编译产物可丢弃。文件工具统一写入数据库并维护事件；P0 受控命令不得绕开工具修改源文件。
- **并发与恢复**：同项目一个活跃 Agent 写入者；写操作使用预期修订和幂等 `toolCallId`。后台任务由可续租的执行者处理，与 HTTP 响应及浏览器标签页生命周期解耦。检查点包含工作区修订、计划位置、最后完成工具与诊断。恢复直接读取当前文件，不依赖重放完整聊天历史重建代码。
- **执行循环**：首次生成、普通修改和直接 Bug Fix 共用 Observe → Decide → Tool → Inspect → Continue/Complete 循环；计划可更新，但不把固定的 BA→Architect→Coder 角色链作为必经门槛。`RequirementSpec`、`AppBlueprint` 按任务需要作为结构化工作区资料保留。
- **生成协议与事件协议**：模型通过具名、Schema 约束的工具调用请求变更，执行器验证完整参数、权限和预期修订后才写入数据库；JSON 等结构化文件优先以对象参数经确定性序列化。Item/Event 由运行时根据真实工具生命周期与提交结果生成，负责呈现、审计和恢复，不能被模型文本伪造为文件写入。单文件调用失败只重试该文件或相应步骤；流式增量不作为可提交代码。
- **工具边界**：文件工具提供列出、搜索、读取、精确写入、补丁和删除；校验工具提供 JSON、Schema、契约、Migration、前后端编译和诊断查询。`run_command` 在 P0 只运行受控检查，保留超时、输出截断、退出码与审计事件。所有路径和资源必须受项目所有权及工作区根限制。
- **诊断与停止**：诊断关联产生它的工作区修订；新写入使旧诊断失效，复验后才能清除。P0 识别相同阻塞诊断无进展并停止；复杂修复策略与浏览器自动验收留给 P2。
- **版本与 Preview**：提交时锁定通过 P0 检查的修订并生成一个不可变版本；Go 全栈版本提交之后创建 Preview BuildJob，静态版本从已提交文件进入现有浏览器 Sandbox。用户看到的状态区分 `committed`、`preview_running`、`preview_succeeded`、`preview_failed`。Preview 失败不回滚已提交代码版本，也不在 P0 自动触发 Agent；发布前检查仍要求现有 Preview 条件。
- **事件协议**：新任务以结构化 Item 和有序事件驱动聊天、计划、工具、诊断、命令及文件面板。`item.started` 可表示调用进行中，`item.completed` 携带执行器确认的最终结果；仅写入事务成功后发出 `file.changed` 成功事件。重要事件和工具结果持久化；刷新先加载快照再按事件序号续传。历史 XML 消息保持只读兼容，新任务不再生成 `<boltArtifact>`。
- **迁移**：新旧消息读取并存，先让新任务走工作区和事件协议，确认静态与 Go 两条主链路后，再移除旧生成路径的运行时依赖；不删除历史消息或既有 `ArtifactVersion`。

## 涉及层与路径

- **路径**：B（新增工作区 Agent 模块，并改造现有项目工作区 UI）。已有主页面与代码面板，但要新增任务 Item、诊断和文件变化呈现，信息与交互结构需要在阶段 3 review。P0 交互重点是计划、工具、诊断、恢复和提交/Preview 状态；交互原型中人工编辑与增强输入只作下一次需求的方向展示。沿用现有 `DESIGN.md` 的视觉 token，仅补充新组件条目，不重做全站视觉系统。
- **涉及层**：数据库模型与迁移（Draft Workspace、文件修订、Agent Run、事件/检查点）；工作区文件服务与执行器；Agent harness 和工具路由；静态/Go 校验与构建服务；任务及文件 API、事件流；现有聊天、代码面板和预览状态 UI；`ArtifactVersion` 提交与 BuildJob 衔接。两个仓库的 Sandbox 协议仅在工作区文件投送需要变化时调整，并做 Generator/Sandbox 兼容验证。
- **设计产物**：阶段 3 已基于现有项目布局制作交互原型；P0 只以运行中、诊断、刷新恢复、取消、双标签冲突及提交/Preview 状态为实施输入。原型里人工编辑与运行中补充要求的控件保留展示但不实施。项目根 `DESIGN.md` 已补工作区组件条目；本 spec 的 AC-UI-1 至 AC-UI-5 已列出信息结构、亮暗主题、窄宽视口、键盘和动态行为的验法。

## 开发批次

### 批次 1：持久 Draft 与工具/诊断基础

- **Goal**：让静态和 Go 文件在数据库 Draft 中可原子读写、隔离执行、恢复，并产生可定位诊断。
- **输入**：本 spec；现有 `ArtifactVersion`/`File` 模型；静态 Sandbox 与 Go Scaffold 契约；本次没有新 UI 设计产物作为此批输入。
- **验收标准**：AC-1 至 AC-4、AC-8 至 AC-10、AC-15 的服务部分、AC-22。
- **交接物**：工作区 schema 与迁移、文件工具、受控命令执行与诊断契约、隔离环境装配、真实数据库测试、供下一批使用的工具接口。

### 批次 2：Agent 循环、恢复与版本提交

- **Goal**：用一套循环完成首次生成和普通修改，失败可恢复，成功可从确定修订提交版本并启动 Preview。
- **输入**：本 spec；批次 1 的工作区/诊断接口；现有 RequirementSpec/AppBlueprint、Go Builder、ArtifactVersion 和 BuildJob 服务；本次没有新 UI 设计产物作为此批输入。
- **验收标准**：AC-5 至 AC-7、AC-11 至 AC-14、AC-17 至 AC-19 的服务部分、AC-23。
- **交接物**：后台 Agent Run、固定脚本模型接缝、可恢复计划与工具循环、幂等版本提交、Preview 衔接、静态与 Go 完整任务测试。

### 批次 3：事件 UI 与真实页面接线

- **Goal**：让用户在现有项目页面看到真实工作区、事件、诊断及两级验证状态，并完成浏览器验收。
- **输入**：本 spec；批次 1、2 的 API 与事件契约；交互原型 `docs/prototypes/2026-10-21-workspace-agent.html` 与项目根 `DESIGN.md`。原型中的人工编辑及增强输入控件只作后续方向展示。
- **验收标准**：AC-6、AC-9、AC-12 至 AC-16、AC-19 至 AC-21 的页面部分；AC-UI-1 至 AC-UI-5。
- **交接物**：事件驱动的计划/工具/诊断 UI、只读工作区代码面板、旧消息兼容、BOT-1 至 BOT-7 与主流程回归证据、开发完成报告。

## 不在范围内

- P0 不把 Preview 编译、健康检查或 API acceptance 失败自动反馈给 Agent；P1 建设 Preview Loop。
- P0 不引入专门的 Bug Fix 子 Agent；用户直接提出的 Bug Fix 由主 Agent 按普通修改处理。P1 子 Agent 与主 Agent 共用工作区文件及事件协议。
- P0 不要求浏览器自动走查生成应用；P2 建设自动浏览器验收。P0 开发验收仍需真实页面 BOT 检查 Prompt Web 自身的工作区体验。
- P0 不实现复杂的修复策略切换；仅保留相同诊断无进展停止条件。
- P0 不提供人工编辑、保存或暂停 Agent 的工作区操作；已有原型中的这些控件仅作后续方向展示。
- P0 不重设计输入框，不实现运行中插话、结构化确认卡、计划批准卡或问题选项卡。计划在 P0 只读展示；遇到必须由用户决策的问题则结束当前执行段并保留 Draft。
- 不重新设计生产发布、数据网关或 Go 应用运行时；维持既有发布前 Preview 门槛。
- 不迁移或删除历史 XML 消息、旧版本及现有部署。
- 不在 Agent 工具中开放不受控的 Shell、外部网络访问或生产发布操作。
