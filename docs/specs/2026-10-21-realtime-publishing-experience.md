# 实时发布体验

## 问题陈述

用户发起发布后，目前只能留在弹窗中看三个粗粒度步骤，并通过每两秒轮询等待最终结果。用户不知道系统正在处理哪一步、是否仍在正常推进，也无法在出错时看到足够清晰的原因和解决办法。发布中心又把历史记录放在显眼位置，没有优先回答用户最关心的三个问题：发布是否成功、现在进行到哪里、失败后怎么办。

## 解决方案

保留发布前检查弹窗，把“发布过程”抽离为独立发布状态页。确认发布后立即进入该页面，通过 SSE 接收当前发布任务的状态和增量日志；页面首先展示用户可理解的结果、阶段和下一步动作，终端式活动流作为可展开的第二层信息。发布完成后活动流冻结为本次记录，发布中心按项目优先展示当前线上状态，历史记录降级为按需查看的详情。

产品流程不增加单独的 staging 阶段。新版本在隔离运行实例中完成构建、启动与验证，只有验证通过才切换公开地址；失败时继续保留原线上版本。

## 用户故事

### 发起发布

- **US-1** 作为准备发布项目的用户，我想先看到版本、文件和可用性检查，以便在开始前知道当前版本是否具备发布条件。
- **US-2** 作为已有线上版本的用户，我想在发布前知道旧版本会持续可用，以便放心启动新发布。
- **US-3** 作为开始发布的用户，我想在确认后进入独立状态页，以便完整查看过程而不受工作区弹窗空间限制。

### 查看实时过程

- **US-4** 作为正在等待发布的用户，我想首先看到当前阶段、完成比例和系统正在做什么，以便判断任务是否正常推进。
- **US-5** 作为需要技术细节的用户，我想展开终端式活动流，以便查看构建、启动和健康检查事件。
- **US-6** 作为查看实时日志的用户，我想默认自动跟随最新事件，以便不必持续滚动。
- **US-7** 作为正在阅读旧日志的用户，我想在向上滚动后暂停自动跟随，以便新事件不会打断阅读。
- **US-8** 作为暂停跟随的用户，我想看到未读事件数量并一键回到最新，以便快速恢复实时视图。
- **US-9** 作为刷新页面或短暂断网的用户，我想恢复当前发布状态并从已读位置继续，以便日志不丢失、不重复。
- **US-10** 作为使用辅助技术的用户，我想让阶段和结果通过文字与语义状态表达，以便不依赖颜色理解进度。

### 处理结果

- **US-11** 作为发布成功的用户，我想立即看到稳定 URL、当前版本和检查结果，以便确认上线完成。
- **US-12** 作为发布成功的用户，我想复制或打开公开地址，以便立即交付给他人。
- **US-13** 作为仍需调整内容的用户，我想返回项目继续修改，以便开始下一轮迭代。
- **US-14** 作为发布失败的用户，我想先知道原线上版本是否受影响，以便判断事故影响。
- **US-15** 作为发布失败的用户，我想看到人话原因、失败阶段和推荐解决办法，以便知道下一步做什么。
- **US-16** 作为排查复杂问题的用户，我想查看并复制完整技术日志，以便自行分析或交给他人处理。
- **US-17** 作为修复失败的用户，我想返回项目并携带失败上下文，以便让 Agent 定向检查并重新发布。

### 管理线上应用

- **US-18** 作为管理多个项目的用户，我想在发布中心先看到每个项目的线上状态、当前版本和最近结果，以便快速发现需要处理的应用。
- **US-19** 作为管理正在发布项目的用户，我想从发布中心直接进入实时状态页，以便继续观察任务。
- **US-20** 作为需要追溯的用户，我想按需展开历史记录和冻结日志，以便排查或比较版本。
- **US-21** 作为需要恢复旧版本的用户，我想在回滚确认时知道 URL、数据和当前版本会怎样变化，以便安全操作。
- **US-22** 作为需要停止公开访问的用户，我想在下线确认时明确访问会停止但数据和版本会保留，以便区分下线与回滚。
- **US-23** 作为首次使用发布中心的用户，我想看到明确的空状态和返回项目入口，以便知道如何完成第一次发布。

## 验收标准

- **AC-1** 发布前检查继续阻止无版本、无文件或全栈预览失败/未完成的版本；检查通过时可确认发布。〔覆盖 US-1, US-2〕
  - **怎么验**：纯函数测试覆盖检查状态组合；真实页面 BOT-1 实际验证可发布与被阻止两种状态。
- **AC-2** 用户确认发布后，系统创建的 deployment 标识进入 URL，并导航到独立状态页；关闭或刷新状态页不会取消后台任务。〔覆盖 US-3, US-9〕
  - **怎么验**：后台测试检查创建响应；真实页面 BOT-1 检查导航 URL、刷新和后台任务状态。
- **AC-3** 状态页把 `QUEUED / BUILDING / TESTING / MIGRATING / STARTING / VERIFYING / SUCCEEDED / FAILED` 映射为稳定的用户阶段、进度和解释，不向主视觉暴露内部枚举。〔覆盖 US-4, US-10〕
  - **怎么验**：纯函数测试逐一覆盖状态映射；真实页面 BOT-1 检查发布中页面文案。
- **AC-4** SSE 仅允许项目所有者订阅指定 deployment，首次连接返回完整快照，后续只发送新增事件和状态变化。〔覆盖 US-5, US-9〕
  - **怎么验**：后台测试检查所有权、404/401、快照与增量事件契约；真实页面 BOT-1 检查单次发布不出现跨项目数据。
- **AC-5** 每条发布活动事件具有 deployment 内单调递增的事件序号、时间、阶段、级别和可读消息；现有纯文本历史日志仍可读取。〔覆盖 US-5, US-9, US-20〕

- **AC-6** 浏览器断线重连时使用最后事件序号恢复；同一事件在活动流中最多出现一次。〔覆盖 US-9〕
  - **怎么验**：纯函数测试检查合并与去重；真实页面 BOT-2 中断连接、恢复后核对事件数量和顺序。
- **AC-7** 活动流展开时默认跟随最新；用户向上滚动离开底部后暂停跟随，显示“回到最新（n）”，点击后恢复跟随并清零未读数。〔覆盖 US-6, US-7, US-8〕
  - **怎么验**：组件测试检查滚动状态机；真实页面 BOT-2 通过真实滚动和新增事件验证交互。
- **AC-8** 发布成功页展示公开 URL、版本、通过的检查、复制、打开网站和继续修改入口；活动流停止追加并可作为冻结记录查看。〔覆盖 US-11, US-12, US-13, US-20〕
  - **怎么验**：组件测试检查成功态操作；真实页面 BOT-3 完成发布并验证链接、剪贴板和冻结状态。

### 主流程回归

本次会改变“从项目工作区发起发布”的稳定主流程，需要新增覆盖发布前弹窗到独立状态页的回归用例，并回归现有生成、预览、发布和公开访问链路。发布失败必须确认不会替换现有 activeDeployment。

## 实现决策

- 发布前检查仍由现有弹窗承担；POST 成功创建 deployment 后立即关闭弹窗并导航到独立状态页。同步发布已经完成时也导航到相同页面。
- 状态页按 deployment 加载快照，并订阅同一资源的 SSE。SSE 使用具名事件 `snapshot`、`activity`、`status`、`complete` 和 `error`；心跳不进入用户日志。
- 发布活动在现有 `BuildJob.log` 中使用版本化 JSONL 保存，不新增数据库表。每条记录包含 `version`、`sequence`、`timestamp`、`stage`、`level`、`message`；解析器兼容既有纯文本行。
- Worker 的状态改变与关键外部动作写入同一活动流。事件序号在单个 BuildJob 内递增；服务器根据最后事件序号返回缺失事件。客户端先应用快照，再按 `jobId + sequence` 去重。
- 用户阶段与内部状态解耦：`QUEUED` 为准备，`BUILDING` 为构建，`TESTING` 为检查产物，`MIGRATING` 为准备数据，`STARTING` 为启动，`VERIFYING` 为验证，`SUCCEEDED` 为已上线，`FAILED` 为未完成。产品文案不出现 staging。
- 对非 Go 的同步静态发布，状态页从 Deployment 生成完成快照；没有 BuildJob 时不展示虚构的实时事件。
- 错误呈现分三层：用户结果与旧版本影响、可操作的原因和建议、可展开的完整技术信息。未知错误使用安全兜底，不根据任意日志字符串生成危险操作建议。
- 发布中心根据 activeDeployment、最新 deployment 和关联 BuildJob 推导项目状态，默认只展示项目卡与最新结果；历史记录按需展开，点击记录打开详情抽屉或进入对应状态页。
- 回滚与下线继续使用现有后台能力，但增加明确确认界面；自动化验收只打开并取消，不执行破坏性操作。
- SSE 设置禁止缓存、保持同源认证，并在终态发送 `complete` 后关闭。客户端在异常关闭时退避重连，页面卸载时主动关闭连接。
- 日志响应在服务端统一截断和脱敏；浏览器只接收展示所需字段，不接收容器环境、数据库凭证或 Worker lease 信息。

## 涉及层与路径

- **路径**：B（新增页面或模块）。需要新增独立发布状态页、活动流模块和 SSE 接口；信息结构已经通过画布上的 A+B 方案及完整用户旅程定稿，不再重复三方案线框选择。
- **涉及层**：
  - 前端组件与模块：发布状态摘要、阶段进度、实时活动流、结果与恢复动作、发布中心项目卡和记录详情。
  - 页面与对接层：独立发布状态页、现有发布弹窗导航、发布中心数据加载与动作。
  - 后端 service：活动事件编解码、状态快照、所有权查询、脱敏与增量读取。
  - 后端 route：deployment 详情与 SSE 事件流。
  - Worker：在关键阶段追加结构化活动事件并记录成功终态。
  - Schema：不新增表、不修改 Prisma schema。
- **设计产物**：已有线框全景图继续作为信息结构依据；阶段 3 只对发布模块运行 `design-system`，补齐亮暗主题、状态颜色、日志样式、间距和组件条目，并创建或更新项目根 `DESIGN.md`。

## 开发批次

### 批次 1：发布事件与实时接口

- **Goal**：建立可恢复、可鉴权、可测试的发布事件源，让任何前端都能稳定获得 deployment 快照和增量活动。
- **输入**：本 spec；现有 BuildJob/Deployment schema；现有 Worker 状态与 `BuildJob.log`；本次无线框实现要求，只消费事件契约。
- **验收标准**：AC-3、AC-4、AC-5、AC-6、AC-9 中错误分类部分、AC-13、AC-14 中后台部分、AC-15。
- **交接物**：发布事件类型与解析器、状态快照 service、SSE route、Worker 事件写入、对应测试，以及供批次 2 使用的稳定前端数据契约。

### 批次 2：发布状态页与发布中心

- **Goal**：按定稿线框和视觉规范完成用户可见的实时发布旅程，并接入批次 1 的契约。
- **输入**：本 spec；`design-refs/` 中发布旅程线框与视觉稿；批次 1 的事件契约；更新后的 `DESIGN.md`。
- **验收标准**：AC-1、AC-2、AC-7、AC-8、AC-9 的页面部分、AC-10、AC-11、AC-12、AC-14 的页面部分，以及全部 AC-UI。
- **交接物**：发布状态页、活动流交互、发布弹窗导航、重构后的发布中心、组件/纯函数测试、BOT-1 至 BOT-6 的证据和开发完成报告。

## 不在范围内

- 不增加面向用户的 staging 发布阶段。
- 不重写 Docker 构建、迁移、运行容器、Traefik 路由或稳定域名机制。
- 不新增 Deployment/BuildJob 之外的审计或事件数据库表。
- 不建立通用通知中心，也不把发布事件协议扩展为整个 Agent 事件协议。
- 不设计手机端专属导航、手势或交互；只保证窄屏可用和无横向溢出。
- 不在本需求中自动执行真实回滚、下线或 production 发布。
- 不把模型用于实时解释每一条日志；错误建议使用确定性分类与安全兜底。
