# Patch-first Workspace Agent

## 问题陈述

当前 Workspace Agent 已经具备 Workspace Manifest、搜索、读取、写入、补丁和校验工具，但工具之间缺少可执行的顺序约束。模型仍可在没有定位证据的情况下读取整个文件、用 `write_file` 覆盖已有文件，或在补丁冲突后反复尝试相同动作。结果是一次修改可能携带大量无关源码进入上下文，也可能覆盖用户已经存在的实现；当任务用于增加功能或修复 Bug 时，运行到步数上限仍未完成的风险较高。

用户需要的不是依靠 prompt 自律的“一次性代码生成器”，而是与 Claude/Codex 类似的 Workspace Agent：先搜索定位，再局部读取，以 Local Patch 修改已有文件，并通过针对性校验收敛。整文件替换只能作为有审计记录的 Guarded Rewrite，而不能成为默认编辑方式。

## 解决方案

为 Workspace Agent 增加由运行时执行的工具策略状态机。普通的已有文件修改必须形成“定位证据 → 当前版本局部读取 → Local Patch → 针对性校验”的闭环；诊断已经提供精确文件和行号时可以省略搜索，但不能省略局部读取。新文件或空文件仍可一次写入。

数据库工作区继续作为唯一事实源。`search_files` 在数据库当前修订上提供接近 `rg` 的路径过滤、字面量或正则搜索、上下文和结果上限。整文件替换被拆分成独立的 `rewrite_file`，只有满足完整读取、哈希匹配、明确理由和异常条件时才能执行，执行后必须立即完成针对性校验并产生独立审计事件。

策略违规不终止整个工作区，而以结构化错误告知模型唯一或有限的下一步；连续两次发生同类策略违规且没有新增证据或文件修订时，运行以 `no_progress` 停止，避免消耗全部步数。

## 用户故事

### 定位与观察

- **US-1** 作为发起功能修改的用户，我想要 Agent 先定位相关代码，再修改文件，以便修改范围与需求相关而不是重写整个项目。
- **US-2** 作为发起 Bug 修复的用户，我想要 Agent 根据诊断或搜索结果读取故障附近的代码，以便把上下文集中在真正的根因上。
- **US-3** 作为 Workspace Agent，我想要使用路径过滤、字面量或正则模式搜索当前修订，以便像使用 `rg` 一样快速缩小候选文件。
- **US-4** 作为 Workspace Agent，我想要在搜索结果中得到有限上下文、行号和截断状态，以便选择下一次局部读取，而不读取整个文件。
- **US-5** 作为 Workspace Agent，我想要在编译或运行诊断已经给出精确文件和行号时直接局部读取，以便不重复无价值的搜索。
- **US-6** 作为用户，我想要所有观察都绑定到明确的工作区修订，以便旧证据不能授权覆盖新版本文件。

### 修改与保护

- **US-7** 作为用户，我想要已有非空文件默认只能通过 Local Patch 修改，以便保留未涉及的实现。
- **US-8** 作为 Workspace Agent，我想要补丁目标必须在当前修订中被局部观察且唯一匹配，以便修改具有可解释的依据。
- **US-9** 作为 Workspace Agent，我想要新文件和空文件可以直接完整写入，以便初始化文件不需要伪造补丁上下文。
- **US-10** 作为用户，我想要普通 `write_file` 无法覆盖已有非空文件，以便 prompt 偏离时运行时仍能阻止大范围替换。
- **US-11** 作为 Workspace Agent，我想要在确实需要大规模重构时使用 Guarded Rewrite，以便极端情况仍有可行路径。
- **US-12** 作为用户，我想要 Guarded Rewrite 验证当前文件哈希、完整读取证据、明确理由及异常触发条件，以便整文件替换不会被当作捷径。
- **US-13** 作为用户，我想要 Guarded Rewrite 后立即执行针对性校验，以便 Agent 不能带着未经验证的大改继续修改其他文件或宣布完成。
- **US-14** 作为维护者，我想要 Guarded Rewrite 产生区别于普通文件修改的审计事件，以便事后识别、分析和统计高风险操作。
- **US-15** 作为用户，我想要补丁冲突不会静默退化为整文件覆盖，以便并发修改或定位错误不会导致代码丢失。

### 纠错与收敛

- **US-16** 作为 Workspace Agent，我想要在策略违规时收到机器可读的错误码、缺失证据和允许的下一步，以便下一轮能够恢复。
- **US-17** 作为用户，我想要连续重复同类策略违规的任务及时停止为 `no_progress`，以便任务不会空转到时间或步数上限。
- **US-18** 作为用户，我想要策略错误保留此前成功写入的修订，以便失败任务仍可诊断和继续。
- **US-19** 作为 Workspace Agent，我想要搜索、局部读取、补丁和校验记录进入最近历史，以便后续决策知道哪些证据仍在当前修订有效。
- **US-20** 作为用户，我想要 Agent 在宣布完成前通过工作区全量校验，以便局部修改不会破坏最终可运行性。

### 可验证的功能增加与 Bug 修复

- **US-21** 作为产品开发者，我想要用同一套机制完成已有应用上的功能增加，以便后续迭代不再依赖整文件再生成。
- **US-22** 作为产品开发者，我想要用同一套机制完成由编译诊断定位的 Bug 修复，以便 Preview 和 Debug Fix 可以复用可靠的底层能力。
- **US-23** 作为维护者，我想要测试覆盖工具顺序、策略拒绝、Guarded Rewrite 和真实页面流程，以便策略不会只存在于 prompt 文本中。

## 验收标准

- **AC-1** `search_files` 支持 `pathGlob`、`mode=literal|regex`、`contextLines` 和 `maxResults`；结果来自指定工作区修订，包含路径、命中行、前后上下文，并明确是否因上限截断。〔覆盖 US-1, US-3, US-4, US-6〕
  - **怎么验**：后台测试在真实 PostgreSQL 中写入多种路径和内容，分别执行路径过滤、字面量、正则、上下文与截断查询，检查返回内容和修订一致。
- **AC-2** 非法正则、越界上下文、过大的结果上限和无效路径模式返回结构化 `INVALID_QUERY`，不读取或修改文件。〔覆盖 US-3, US-4〕
  - **怎么验**：纯函数测试检查查询参数规范化；后台测试检查服务返回错误且工作区修订不变。
- **AC-3** 普通已有文件修改必须先在当前修订获得该路径的定位证据，再通过 `read_file_range` 观察覆盖补丁目标的范围；诊断包含精确文件和行号时可替代搜索证据。〔覆盖 US-1, US-2, US-5, US-6, US-7, US-8〕
  - **怎么验**：纯函数测试输入不同证据序列，检查可用动作；后台测试用脚本模型分别执行标准搜索路径和诊断捷径，确认补丁成功。
- **AC-4** 没有当前修订局部读取证据时调用 `patch_file`，返回 `OBSERVATION_REQUIRED`，其中包含目标路径、缺失证据和允许的 `search_files`/`read_file_range` 动作；文件及修订保持不变。〔覆盖 US-6, US-8, US-16, US-18〕
  - **怎么验**：后台测试直接对已有文件补丁，检查结构化错误、允许动作和数据库修订。
- **AC-5** 局部读取存在但不覆盖 `oldText`，或证据属于旧修订时，`patch_file` 返回 `PATCH_REQUIRED` 或 `OBSERVATION_REQUIRED`，不执行隐式整文件写入。〔覆盖 US-6, US-8, US-15, US-16〕
  - **怎么验**：纯函数测试覆盖证据失效与范围不覆盖；后台测试检查补丁冲突后文件哈希不变。
- **AC-6** `write_file` 只允许创建当前修订不存在的路径，或写入当前内容为空的文件；对已有非空文件返回 `PATCH_REQUIRED` 并指向 `read_file_range` 与 `patch_file`。〔覆盖 US-7, US-9, US-10, US-16〕
  - **怎么验**：后台测试分别创建新文件、初始化空文件和覆盖已有非空文件，检查前两者成功、后者无修订变化。
- **AC-7** `read_file` 不再作为普通修改的默认观察工具；完整读取只产生 Guarded Rewrite 所需证据，并受文件大小上限约束，普通修改的恢复建议始终优先给出 `read_file_range`。〔覆盖 US-1, US-2, US-11, US-12〕
  - **怎么验**：纯函数测试检查完整读取证据类型和后续允许动作；后台测试检查超限文件不能被完整读取。
- **AC-8** `rewrite_file` 仅在以下条件全部成立时可执行：目标是已有非空文件；已完整读取该文件的当前修订；参数含匹配的 `expectedSha256` 和非空 `reason`；并且当前修订中该路径已发生两次 `PATCH_CONFLICT`，或请求声明且运行时确认替换范围覆盖文件主体。〔覆盖 US-11, US-12, US-15〕
  - **怎么验**：纯函数测试逐项缺失前置条件；后台测试验证只有完整条件组合能产生新修订，旧哈希或伪造理由均被拒绝。
- **AC-9** Guarded Rewrite 成功后运行进入“待针对性校验”状态；在相应校验成功前，除观察、诊断和校验外的其他修改及 `complete` 均被拒绝。〔覆盖 US-13, US-16, US-20〕
  - **怎么验**：后台测试在 rewrite 后尝试修改其他文件和完成任务，检查被拒绝；随后运行适用的定向命令并确认状态解锁。
- **AC-10** Guarded Rewrite 产生独立审计事件，至少记录路径、前后哈希、修订、理由、采用的异常条件和校验结果；普通 Local Patch 不产生该事件。〔覆盖 US-14, US-19〕
  - **怎么验**：后台测试查询 Agent 事件，检查 rewrite 审计载荷不含源代码且与修订记录一致。
- **AC-11** 策略错误统一返回 `{ code, message, requiredEvidence, allowedNextActions }`；该结果进入下一轮 `previousResult` 和有界历史，但不把整文件内容写入历史。〔覆盖 US-16, US-19〕
  - **怎么验**：纯函数测试检查错误契约；后台测试检查下一次脚本模型观察到恢复信息且历史不含文件全文。
- **AC-12** 在工作区修订、证据集合均未变化时，连续两次相同策略错误使运行进入 `NO_PROGRESS`，事件原因是 `no_progress`；不同恢复动作或新增证据会重置该计数。〔覆盖 US-17, US-18〕
  - **怎么验**：后台测试驱动脚本模型重复违规，再驱动一次先读取后修复的序列，分别检查停止与恢复结果。
- **AC-13** Local Patch 成功后旧修订证据失效；Agent 必须基于新修订重新定位或读取下一处修改，且每次修改仍保留不可变文件修订和幂等写入收据。〔覆盖 US-6, US-18, US-19〕
  - **怎么验**：后台测试在连续两个补丁之间复用旧证据，检查第二次被拒绝；补充当前修订证据后成功，并核对修订链。
- **AC-14** 功能增加任务能够对已有前端文件完成搜索、局部读取、Local Patch、针对性校验和最终全量校验，任务不使用 Guarded Rewrite 且进入可发布状态。〔覆盖 US-20, US-21, US-23〕
  - **怎么验**：后台测试用固定脚本模型和真实 PostgreSQL 验证完整执行序列；真实页面 BOT-1 在真实栈发起一次小功能修改并检查最终状态和操作记录。
- **AC-15** 带精确编译诊断的 Bug 修复任务能够跳过搜索，但必须局部读取诊断范围、执行 Local Patch、重新运行对应命令并最终通过全量校验。〔覆盖 US-2, US-5, US-20, US-22, US-23〕
  - **怎么验**：后台测试注入带文件和行号的诊断并验证工具序列；真实页面 BOT-2 在真实栈发起一次可复现修复并检查 Preview 恢复。
- **AC-16** 模型工具说明明确普通路径为 `search_files → read_file_range → patch_file → targeted validation`，并说明 `write_file` 与 `rewrite_file` 的限制；运行时测试证明绕过说明仍会被拒绝。〔覆盖 US-1, US-7, US-10, US-11, US-23〕
  - **怎么验**：纯函数测试检查工具 schema 和系统说明；后台测试直接发送违规工具调用，确认不是仅靠 prompt 限定。

### 主流程回归

本次改动会影响所有“生成后继续增加功能”和“根据诊断修复 Bug”的 Workspace Agent 主流程，也会改变初次生成中对已创建文件的后续修改方式。需要为 `pnpm e2e:regression` 增加一条确定性的已有项目增量修改用例，至少覆盖“创建/载入工作区 → 搜索 → 局部读取 → 补丁 → 校验 → READY_TO_VALIDATE”。初次生成新文件仍走 `write_file`，现有首次生成回归必须保留。

## 实现决策

- 在 Agent 运行时引入按“运行、工作区修订、文件路径”归属的证据台账。证据至少区分搜索命中、诊断定位、局部读取、完整读取、补丁冲突和待校验 Guarded Rewrite；工作区修订变化后，旧修订证据不能授权新修改。
- 工具策略由运行时在执行变更前判定，而不是仅写入模型提示。模型适配器仍提供推荐顺序，但不能绕过服务器规则。
- 增强 `search_files` 的查询契约：支持路径 glob、字面量/正则模式、有限上下文和结果上限。实现继续遍历数据库中的指定不可变修订，不为搜索创建临时目录，也不调用宿主机 shell。
- 普通修改已有非空文件只能使用 `patch_file`。补丁必须对当前文件唯一匹配，并且唯一目标位于当前修订已读取的行范围内；补丁冲突只产生诊断和证据，不自动改用整文件覆盖。
- `write_file` 只承担新文件或空文件初始化。结构化 JSON 专用写入工具遵循相同的“新/空文件”限制；对已有 JSON 的变更也必须通过 Local Patch，除非进入 Guarded Rewrite。
- 新增显式 `rewrite_file` 工具。其请求包含完整内容、`expectedSha256`、`reason` 和异常条件声明。运行时验证完整读取证据，以及“两次补丁冲突”或“替换覆盖文件主体”的客观条件；后者依据新旧内容差异比例判定，不接受模型单方面声明。
- Guarded Rewrite 成功后设置校验债务。按文件类型和 Runtime Type 选择可接受的针对性校验；债务清除前禁止新的 mutation 和 `complete`。最终 `complete` 仍必须执行现有工作区全量校验。
- Guarded Rewrite 使用独立审计事件，载荷只保存元数据、理由、条件与校验结果，不保存源文件内容。普通 `file.changed` 事件和不可变修订记录继续保留。
- 策略错误使用统一机器可读契约，并返回有限的下一步集合。`OBSERVATION_REQUIRED` 表示缺少当前修订定位或读取证据；`PATCH_REQUIRED` 表示操作必须改为 Local Patch；原有 `PATCH_CONFLICT` 保留为补丁目标不唯一或不存在。
- 连续违规按错误码、目标路径、工作区修订和证据指纹判定。相同指纹连续出现两次时停止为 `NO_PROGRESS`；成功观察、修订变化或采取不同允许动作会重置计数。
- 最近历史继续保持有界，只保存动作、路径、结果摘要和结构化策略信息，不加入搜索返回的所有上下文或完整文件正文。
- 不改变 Workspace Manifest 的职责：每轮只向模型提供路径、哈希和修订，不提供全项目源码。

## 涉及层与路径

- **路径**：D（不碰 UI）。本次改动是 Workspace Agent 的工具契约、数据库工作区服务、运行时策略、事件与测试改造；现有消息区和操作记录继续消费通用 Agent 事件，不新增页面、组件或视觉交互，因此不进入线框图或设计系统阶段。
- **涉及层**：后端 service（搜索、读取、补丁、重写和审计）、Agent runtime（证据台账、策略状态机、无进展判定）、模型工具契约（工具 schema 与系统说明）、持久化（若现有步骤/事件 JSON 无法可靠恢复证据，则增加最小 schema；优先从不可变步骤与事件重建）、Worker 执行与后台/全栈测试。
- **设计产物**：不新增线框图，不修改 `DESIGN.md`。规格图只用于解释 Agent 工具状态机，不代表 UI 方案。

## 不在范围内

- 不把数据库工作区物化到磁盘后调用真实 `rg`；目标是提供等价的定位能力，不改变事实源。
- 不允许模型执行任意 shell、任意文件系统读取或任意测试命令。
- 不重新设计消息区、Preview、代码浏览器或任务卡片的视觉表现。
- 不在本次引入语义索引、向量检索、AST 自动重写或跨仓库搜索。
- 不保证任意真实模型每次都选择最优工具；本次保证的是违规动作不能破坏工作区，并为模型提供可恢复路径。
- 不取消最终工作区全量校验，也不以针对性校验替代发布前验收。

## 补充说明

- 本规格遵循 `CONTEXT.md` 中 Workspace Agent、Workspace Manifest、Observation Tool、Local Patch、Guarded Rewrite 的术语。
- 架构约束见 `docs/adr/0001-tool-guided-workspace-mutations.md`：数据库工作区保持唯一事实源，已有文件 patch-first，整文件替换为受控例外。
- 最大风险是策略过严导致初次生成或多文件重构消耗更多步骤。通过“新/空文件允许完整写入”、诊断捷径、结构化恢复动作以及 Guarded Rewrite 例外控制该风险；不能通过重新开放普通覆盖来规避。
- 另一个风险是 Agent 在重启或 Worker 续租后丢失证据。实现必须能从持久化步骤、事件和当前修订恢复等价证据，不能只依赖进程内存。
