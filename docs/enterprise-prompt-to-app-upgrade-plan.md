# 企业级 Prompt-to-App 升级与部署方案

> 状态：提案  
> 适用项目：AI Component Generator  
> 更新时间：2026-09-25

## 1. 背景

当前项目已经具备自然语言生成 React 页面、实时预览、版本管理和分享能力，但产品形态仍接近“Prompt-to-Web 原型”。通用网页生成已经有较多成熟产品，继续只强化页面生成并不能形成足够清晰的差异化。

本次升级将产品定位调整为：

> 面向企业员工的 AI 应用构建与发布平台。员工可以使用企业自定义组件库，通过自然语言生成带真实数据、权限和发布能力的内部网页或轻量业务应用。

平台重点解决以下问题：

1. 普通员工即使拥有 AI，也难以准确表达并实现业务需求。
2. 企业已有设计规范和组件库，通用生成工具难以保持一致性。
3. 非技术用户不会构建、部署、配置域名和维护运行环境。
4. 企业不希望业务数据、代码和密钥默认存储在外部 SaaS 中。
5. 生成结果需要从“可预览页面”升级为“可持续运行的真实应用”。

本项目同时作为求职作品，需要完整体现产品判断、AI 工程、数据建模、多租户、安全隔离、部署发布和可观测性能力。

## 2. 产品边界

### 2.1 第一阶段目标

第一阶段交付一个可演示、可真实使用的最小闭环：

```text
描述需求
  → AI 选择企业组件并生成应用
  → 定义数据表和字段
  → 生成真实 CRUD 页面
  → 实时预览
  → 一键发布
  → 通过独立子域名访问
  → 修改后重新发布或回滚
```

### 2.2 第一阶段不做

- 不做任意后端代码生成和运行。
- 不允许生成代码直接持有数据库管理员凭证。
- 不为每个静态应用长期运行独立容器。
- 不做 Kubernetes、多地域或跨云调度。
- 不在第一阶段支持用户购买域名。
- 不承诺生产级企业 SLA。
- 不允许 AI 不经校验直接执行任意 SQL 或数据库迁移。

### 2.3 核心差异化

- 企业组件库约束，而不是完全自由生成 UI。
- 面向企业内部应用，而不是只生成营销页面。
- 从生成、数据、权限到发布形成闭环。
- 支持在企业网络或企业服务器中私有化部署。
- 生成应用通过统一运行时访问数据，安全策略由平台控制。

## 3. 总体架构

建议将系统划分为控制面、构建面和运行面。

```text
                         ┌──────────────────────┐
                         │ studio.example.com   │
                         │ 生成器与管理后台       │
                         └──────────┬───────────┘
                                    │
                                Traefik
                    ┌───────────────┼────────────────┐
                    │               │                │
          ┌─────────▼───────┐ ┌────▼──────────┐ ┌───▼────────────────┐
          │ Control Plane   │ │ Build Worker  │ │ App Runtime        │
          │ 项目/版本/权限    │ │ 构建发布产物    │ │ *.apps.example.com│
          └─────────┬───────┘ └────┬──────────┘ └───┬────────────────┘
                    │              │                │
          ┌─────────▼──────────────▼───┐      ┌─────▼──────────┐
          │ PostgreSQL: platform data │      │ Data Gateway   │
          └────────────────────────────┘      └─────┬──────────┘
                                                   │
                                   ┌───────────────▼──────────────┐
                                   │ PostgreSQL: application data│
                                   └──────────────────────────────┘

          ┌──────────────────────────────────────────────────────┐
          │ MinIO / S3：构建产物、图片和附件                       │
          └──────────────────────────────────────────────────────┘
```

### 3.1 控制面

负责：

- 用户、组织和成员关系。
- 项目与应用配置。
- 企业组件库配置。
- AI 会话与生成版本。
- 数据模型定义。
- 发布记录、域名和当前生产版本。
- 权限策略和审计记录。

现有 Next.js 应用可以继续承担控制面的 UI 与 API；现有 Prisma 数据模型在此基础上演进。

### 3.2 构建面

构建任务必须与主 Web 进程解耦。发布时创建异步任务，由 Worker 完成：

1. 读取指定 ArtifactVersion。
2. 安装或解析白名单依赖。
3. 在受限制环境中构建。
4. 执行静态检查和安全检查。
5. 将构建产物上传至 MinIO/S3。
6. 更新 Deployment 状态。
7. 原子切换当前生产版本。

构建失败不得影响已经发布的版本。

### 3.3 运行面

第一阶段使用统一应用运行时，而不是一应用一个容器：

1. Traefik 将 `*.apps.example.com` 转发到 App Runtime。
2. Runtime 根据请求 Host 解析应用 slug。
3. 查询应用当前生产 Deployment。
4. 从对象存储读取对应静态资源。
5. 返回 SPA 入口或静态文件。

只有应用需要独立后端、特殊依赖或长时间任务时，才进入独立容器运行模式。

## 4. 域名和部署方案

### 4.1 推荐拓扑

```text
studio.example.com       平台管理端
api.example.com          数据与平台 API
assets.example.com       构建产物和附件
*.apps.example.com       用户发布的应用
```

DNS 配置：

```text
A     studio.example.com       → 服务器公网 IP
A     api.example.com          → 服务器公网 IP
A     assets.example.com       → 服务器公网 IP
A     *.apps.example.com       → 服务器公网 IP
```

### 4.2 Traefik 的职责

- 监听 80/443 端口。
- HTTP 自动跳转 HTTPS。
- 根据 Host 路由到对应平台服务。
- 终止 TLS。
- 统一添加安全响应头。
- 输出访问日志与指标。

Traefik 不负责：

- 构建用户项目。
- 保存发布状态。
- 管理应用版本。
- 判断用户数据权限。
- 为每个应用自动创建数据库。

### 4.3 HTTPS

通配符证书 `*.apps.example.com` 应通过 DNS-01 自动申请和续签。DNS API 凭证使用 Docker Secret 或独立密钥文件保存，不写入镜像、源码或容器标签。

### 4.4 Traefik 安全基线

- 设置 `exposedByDefault=false`。
- 只有带显式标签的服务允许被发现。
- Dashboard 不开放到公网，或至少增加认证与 IP 限制。
- Docker socket 使用只读挂载；更严格的部署应增加 socket proxy。
- 平台、运行时、数据库、构建器使用不同 Docker 网络。
- PostgreSQL 和 Redis 不映射公网端口。
- 生产环境使用固定镜像版本，不使用 `latest`。

### 4.5 备案边界

个人备案域名可用于非经营性作品演示，但公开允许用户持续发布内容或进行商业化之前，需要确认备案主体、实际服务内容、云服务接入要求以及可能涉及的经营许可。

作品集阶段应清晰标注：

> 本平台为个人技术演示，不建议上传企业生产数据。

## 5. 数据库方案决策

### 5.1 决策

第一阶段采用：

> PostgreSQL + 自建 Data Gateway + 元数据驱动的 JSONB 应用数据模型。

平台元数据和生成应用数据至少进行逻辑分离；生产环境建议使用两个数据库，开发环境可以在一个 PostgreSQL 实例中使用两个数据库。

```text
platform_db   平台控制数据，使用 Prisma 管理迁移
runtime_db    用户应用数据，通过 Data Gateway 访问
```

### 5.2 为什么不直接让生成应用访问数据库

生成代码属于不可信代码。如果直接连接数据库，将产生以下风险：

- 数据库凭证泄露到浏览器。
- 越权读取其他组织或应用的数据。
- AI 生成错误 SQL 导致数据删除或破坏。
- 无法统一实现审计、限流和字段权限。
- 数据结构变更无法可靠回滚。

因此，所有生成应用只能调用平台提供的受控 SDK；SDK 只能访问 Data Gateway。

```text
Generated App
    ↓ @platform/data-sdk
Data Gateway
    ↓ 认证、授权、校验、审计、限流
runtime_db
```

### 5.3 动态数据模型

建议核心模型包括：

#### AppCollection

描述应用中的一个业务集合，例如客户、订单或库存。

| 字段 | 说明 |
|---|---|
| id | 集合 ID |
| organizationId | 所属组织 |
| appId | 所属应用 |
| name | 稳定内部名称 |
| displayName | 展示名称 |
| schema | JSON Schema 或平台字段定义 |
| version | 结构版本 |
| createdAt | 创建时间 |
| updatedAt | 更新时间 |

#### AppRecord

保存真实业务记录。

| 字段 | 说明 |
|---|---|
| id | 记录 ID |
| organizationId | 所属组织 |
| appId | 所属应用 |
| collectionId | 所属集合 |
| data | JSONB 业务数据 |
| createdBy | 创建者 |
| updatedBy | 最后修改者 |
| createdAt | 创建时间 |
| updatedAt | 更新时间 |
| deletedAt | 软删除时间 |

常用查询字段应建立表达式索引。随着业务成熟，可将高频或大型集合迁移为物理表。

### 5.4 Data Gateway 职责

- 验证会话或 JWT。
- 解析组织、应用和当前用户。
- 检查应用是否已发布及是否允许访问。
- 检查集合级操作权限。
- 检查字段级读写权限。
- 根据 Collection Schema 校验输入。
- 使用参数化查询访问 PostgreSQL。
- 注入 `organizationId`、`appId` 和审计字段。
- 限制分页大小、查询复杂度和写入频率。
- 写入不可由普通用户修改的审计日志。
- 隐藏数据库结构和内部错误。

建议第一阶段仅提供有限 API：

```text
GET    /v1/apps/:appId/collections/:name/records
GET    /v1/apps/:appId/collections/:name/records/:id
POST   /v1/apps/:appId/collections/:name/records
PATCH  /v1/apps/:appId/collections/:name/records/:id
DELETE /v1/apps/:appId/collections/:name/records/:id
```

查询参数必须使用白名单，不接受任意 SQL、任意表达式或任意数据库函数。

### 5.5 多租户隔离

第一阶段采用共享数据库、共享表，并在每条业务记录上保存 `organizationId` 和 `appId`。

隔离至少包含两层：

1. Data Gateway 应用层授权。
2. PostgreSQL Row-Level Security 作为数据库层防线。

后续可以提供三个部署级别：

| 级别 | 隔离方式 | 适用场景 |
|---|---|---|
| 标准版 | 共享库共享表 + RLS | 小团队和普通内部应用 |
| 企业版 | 每组织独立 Schema | 更强逻辑隔离和独立导出 |
| 私有版 | 每组织独立数据库或独立部署 | 合规、敏感数据和内网环境 |

### 5.6 为什么暂不选完整自托管 Supabase

Supabase 自托管可以提供 Auth、PostgREST、Realtime、Storage 和 Studio，适合快速构建完整 BaaS，但当前项目已经使用 Auth.js 和 Prisma。立即引入完整 Supabase 会产生：

- 两套认证体系的边界问题。
- 更多容器和运维组件。
- 平台权限与 Supabase RLS 的双重配置。
- 对动态多应用模型的额外适配。
- 自托管备份、监控、升级和安全加固成本。

因此第一阶段保留 PostgreSQL 作为核心，自己实现受控数据入口。Supabase、Directus、Hasura 或企业已有 API 可在后续作为数据源连接器提供。

## 6. 推荐核心数据模型

现有 `User → Thread → Artifact → ArtifactVersion → File` 可以保留，但需要新增业务层概念。

```text
Organization
├── OrganizationMember
├── ComponentLibrary
└── Project / App
    ├── Thread
    ├── Artifact
    │   └── ArtifactVersion
    ├── AppCollection
    │   └── AppRecord
    ├── AppRole
    │   └── AppPermission
    ├── Deployment
    ├── Domain
    ├── EnvironmentVariable
    └── AuditLog
```

### 6.1 建议新增实体

| 实体 | 用途 |
|---|---|
| Organization | 企业或团队租户 |
| OrganizationMember | 成员及组织角色 |
| Project | 独立应用项目，不再以聊天线程代替项目 |
| ComponentLibrary | 企业组件和设计约束 |
| Deployment | 一次构建与发布记录 |
| Domain | 平台子域名和未来自定义域名 |
| AppCollection | 动态业务表定义 |
| AppRecord | 真实业务数据 |
| AppRole | 应用内角色 |
| AppPermission | 集合、操作和字段权限 |
| AuditLog | 数据修改与管理操作记录 |
| EnvironmentVariable | 加密保存的服务端配置 |

`Thread` 应成为 Project 下的 AI 协作会话，而不是业务项目本身。

## 7. 真实数据生成流程

AI 不直接输出可执行 SQL，而是输出结构化的数据模型提案：

```json
{
  "collections": [
    {
      "name": "customers",
      "displayName": "客户",
      "fields": [
        { "name": "name", "type": "text", "required": true },
        { "name": "phone", "type": "text" },
        {
          "name": "level",
          "type": "select",
          "options": ["普通", "重要"]
        }
      ]
    }
  ]
}
```

平台处理流程：

1. 使用严格 Schema 验证 AI 输出。
2. 展示数据模型供用户确认。
3. 保存 Collection 元数据版本。
4. 生成对应页面和 Data SDK 调用。
5. 发布前检查页面引用的数据集合是否存在。
6. 数据结构变化必须生成可审阅的变更计划。

删除字段默认只隐藏，不立即删除历史数据。破坏性变更需要二次确认并记录审计日志。

## 8. 发布与回滚

### 8.1 发布状态机

```text
DRAFT
  → QUEUED
  → BUILDING
  → VALIDATING
  → READY
  → ACTIVE

失败分支：FAILED
历史版本：SUPERSEDED
```

### 8.2 发布步骤

1. 用户选择 ArtifactVersion 并点击发布。
2. 创建不可变 Deployment 记录。
3. Worker 构建对应代码版本。
4. 执行依赖、内容、安全和体积检查。
5. 上传带内容哈希的静态产物。
6. 执行健康检查。
7. 将 Project 的 activeDeploymentId 原子切换到新版本。
8. 保留旧版本用于回滚。

### 8.3 回滚

回滚不重新构建，只将 `activeDeploymentId` 指向历史 READY 版本。数据结构变更与代码发布必须分离，避免代码回滚导致数据丢失。

## 9. 安全设计

### 9.1 信任边界

以下内容均视为不可信输入：

- 用户 Prompt。
- 上传的图片和文件。
- AI 返回内容。
- AI 生成的源代码。
- 生成应用提交的数据。
- MCP 或外部 API 的响应。

### 9.2 构建安全

- 构建器不持有生产数据库凭证。
- 禁止 Docker privileged 模式。
- 限制 CPU、内存、磁盘和执行时间。
- 默认禁止构建环境访问内网。
- npm 依赖使用白名单或受控依赖目录。
- 禁止任意安装脚本，或在隔离环境执行。
- 构建产物进行恶意代码和敏感信息检查。

### 9.3 运行安全

- 生成应用与管理后台使用不同源和 Cookie 范围。
- 设置 CSP、frame-ancestors 和其他安全头。
- 用户内容不得共享平台管理端域名。
- 服务端密钥不进入生成文件和浏览器。
- 对公开应用增加速率限制和请求体大小限制。
- 敏感操作写入审计日志。
- 支持应用关闭公开访问或要求登录。

### 9.4 数据安全

- 默认拒绝所有未配置权限的数据访问。
- 数据查询必须包含组织和应用边界。
- PostgreSQL 账户遵循最小权限原则。
- 定期备份并验证恢复流程。
- 删除组织或项目采用延迟删除机制。
- 日志中对 Token、密码和业务敏感字段脱敏。

## 10. 组件库能力

企业组件库不应只是附加到 Prompt 的一段文字，而应成为可管理资产。

每个组件需要登记：

- 包名和允许版本。
- 组件名称和用途。
- Props Schema。
- 示例代码。
- 设计规范和禁用规则。
- 可用数据字段类型。
- 是否允许在运行时使用。

AI 生成流程应先检索组件清单，再产生结构化页面计划，最后生成代码。构建器只能解析平台允许的包和版本。

第一阶段可优先支持 Ant Design；第二阶段再允许企业上传自己的 npm 私有包和组件元数据。

## 11. 分阶段实施路线

### Phase 0：工程基线

- 梳理现有预览、Artifact 和 Share 流程。
- 增加 Organization 和 Project 概念。
- 将 Thread 调整为 Project 下的会话。
- 增加统一配置校验、日志和健康检查。
- 建立 Docker Compose 开发与生产基线。

验收标准：现有生成和预览功能没有回归，用户数据具备组织和项目归属。

### Phase 1：一键发布

- 新增 Deployment 与 Domain 模型。
- 实现异步构建 Worker。
- 使用 MinIO/S3 保存不可变构建产物。
- 实现 App Runtime。
- 配置 Traefik 与 `*.apps.example.com`。
- 实现发布、重新发布、下线和回滚。

验收标准：任意已生成版本可发布到稳定子域名；发布失败不影响旧版本；可以一键回滚。

### Phase 2：真实数据

- 新增 Collection Schema 编辑器。
- 新增 AppRecord JSONB 存储。
- 实现 Data Gateway 和前端 SDK。
- 支持表格、详情、表单和基础筛选。
- 增加 RLS、审计和限流。
- AI 可生成数据模型提案，但需要用户确认。

验收标准：生成一个客户管理应用，能够新增、查询、修改和删除真实数据，且不同应用不能互相访问数据。

### Phase 3：企业能力

- 组织成员和 RBAC。
- 应用级访问控制。
- 字段级权限。
- 文件上传和 MinIO。
- 企业组件库注册与版本锁定。
- 环境变量和 Secret 管理。
- 操作审计与数据导出。

验收标准：管理员、编辑者和只读成员看到并执行不同操作；所有敏感操作可追踪。

### Phase 4：私有化与连接器

- 完整离线或内网部署包。
- OIDC/LDAP/企业身份源。
- 企业数据库和 HTTP API 连接器。
- 本地模型与外部模型切换。
- 每组织独立 Schema 或数据库。
- 备份、恢复、指标和告警。

## 12. 求职演示建议

建议准备一个端到端演示案例，例如“客户拜访管理”：

1. 输入业务需求。
2. AI 使用指定企业组件库生成页面。
3. AI 提出客户和拜访记录的数据模型。
4. 用户确认字段。
5. 页面立即连接真实数据库进行 CRUD。
6. 点击发布，获得独立子域名。
7. 修改需求后生成新版本并重新发布。
8. 演示一键回滚。
9. 使用另一个账号证明租户和角色隔离。
10. 展示审计日志和私有化部署拓扑。

面试讲解重点不是“调用了哪个模型”，而是：

- 如何约束生成结果。
- 如何让不可信代码安全访问真实数据。
- 如何实现多租户隔离。
- 如何实现稳定发布和回滚。
- 如何让系统从单机演进到企业私有化。

## 13. 技术选型摘要

| 领域 | 第一阶段选择 | 说明 |
|---|---|---|
| Web 平台 | Next.js + React | 延续现有项目 |
| ORM | Prisma | 仅管理稳定的平台控制数据 |
| 数据库 | PostgreSQL | 平台数据和应用数据逻辑分离 |
| 动态数据 | Collection 元数据 + JSONB Record | 避免 AI 任意执行 DDL |
| 数据访问 | 自建 Data Gateway | 集中授权、校验、审计和限流 |
| 反向代理 | Traefik | 域名路由和 TLS |
| 发布运行时 | 统一静态 App Runtime | 避免一应用一容器 |
| 构建任务 | 独立 Worker + Queue | 与 Web 请求解耦 |
| 对象存储 | MinIO 或 S3 兼容服务 | 保存构建产物和附件 |
| 权限 | 应用层 RBAC + PostgreSQL RLS | 双层隔离 |
| 部署 | Docker Compose | 适合单机作品演示和早期交付 |

## 14. 最终决策

1. 产品从 Prompt-to-Web 升级为企业 Prompt-to-App 平台。
2. Traefik 保留为统一入口，但不作为发布状态管理器。
3. 第一阶段使用通配符子域名，不做用户自定义顶级域名。
4. 静态应用使用统一运行时，不采用一应用一容器。
5. PostgreSQL 继续作为核心数据库。
6. 平台数据与生成应用数据分离。
7. 生成应用只能通过 Data Gateway 访问真实数据。
8. 动态业务数据第一阶段采用元数据 + JSONB 模型。
9. AI 只能生成结构化数据模型提案，不能直接执行任意 SQL。
10. 企业隔离能力从共享表 + RLS，逐步演进到独立 Schema 或独立数据库。

## 15. 待确认问题

进入实现前仍需明确：

1. 第一批重点应用是 CRUD 管理应用，还是数据看板、审批或表单收集？
2. 发布应用默认公开，还是必须登录后访问？
3. 平台账号是否同时作为生成应用的账号体系？
4. 企业组件库第一阶段通过源码目录、npm 包还是组件元数据接入？
5. 是否允许应用访问外部 API？如果允许，密钥由谁提供和管理？
6. 数据模型变化是否必须经过人工确认？
7. 第一阶段是否需要附件上传？
8. 是否需要支持企业将项目和数据完整导出？
